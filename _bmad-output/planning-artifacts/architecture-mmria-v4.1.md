# Architecture: MMRIA V4.1

_Generated by Winston (System Architect) — 2026-06-12_

---

## 1. Overview

MMRIA V4.1 is a **brownfield maintenance release** on an existing .NET 9 MVC application. No new services, frameworks, or infrastructure are introduced. Every architectural decision in this document is scoped to the smallest effective change that satisfies the PRD.

The four feature areas map to two distinct change categories:

| Category | FRs | Nature |
|---|---|---|
| Client-side JavaScript defect fixes | FR-1 (editor fidelity) | Behavioral repair in `wwwroot/scripts` |
| Configuration externalization | FR-2, FR-3, FR-4 | Values moved from code/static assets to CouchDB config + server startup |

## 2. Existing Architecture — Relevant Surfaces

Before recording decisions, here is the canonical picture of each surface that V4.1 touches.

### 2.1 Stack

| Layer | Technology | Notes |
|---|---|---|
| Web host | .NET 9 MVC — `mmria-server` | Controllers, Razor views, Akka.NET actors, Quartz jobs |
| Shared libraries | `mmria.common` — `SharedLibraries/<Feature>/Manager` + `DAL` | Preferred home for all new business logic |
| Background services | `mmria.services` — Akka.NET + Quartz | Out of scope for V4.1 |
| Database | CouchDB — per-jurisdiction tenant databases | System of record; config doc loaded at startup |
| Client | Vanilla JavaScript — `wwwroot/scripts` | Metadata-driven form renderer; no build step |

### 2.2 Configuration loading

`OverridableConfiguration` (in `mmria.common/couchdb/configuration/configuration.cs`) holds two maps:

```csharp
Dictionary<string, string>              name_value     // string scalars
Dictionary<string, DBConfigurationDetail> detail_list  // complex objects
```

Loaded at server startup. Controllers access it via `tenantRuntime.RequireConfiguration()` then `configuration.GetString(key)` / `GetInteger(key)`. This is the **extension point** for all V4.1 config values.

### 2.3 Client-side form rendering pipeline

1. Case page (`wwwroot/scripts/case/index.js`) calls `get_case_set()`, which loads case data and metadata from CouchDB via API.
2. `page_renderer.js` dispatches rendering by metadata field type.
3. `chart.js` (in `editor/page_renderer/`) renders repeating-record grids, including vitals grids.
4. `p_post_html_render` callbacks bind events after DOM insertion.
5. `eval(post_html_call_back.join('\n'))` executes accumulated callbacks.

### 2.4 Case narrative editor

- Field type: HTML `textarea` (not TinyMCE or Quill).
- Save snapshot: `mmria_get_narrative_save_snapshot()` in `case/index.js`.
- Content stored as HTML at `g_data.case_narrative.case_opening_overview`.
- Paste handler: `page_render_create_onpaste_event()` in `case/index.js`.
- Prior line-break fix candidate: `textarea_control_strip_html_attributes()` call — currently commented out near line 4356 in `case/index.js`.

## 3. Feature Architecture

### FR-1 — Case Narrative Editor Fidelity

All three sub-requirements are defect fixes on two JavaScript functions in `wwwroot/scripts/case/index.js`. No server-side changes are required for FR-1. Print and PDF already render correctly, confirming the defect is strictly on the client-side save/serialization path and the paste handler.

#### FR-1 — Overriding constraint: do not change the generated HTML structure

> **This constraint takes precedence over every implementation decision in FR-1.**

The PDF and HTML print generators are tightly coupled to the HTML structure stored in the narrative field. Any structural change to the generated HTML — new wrapper elements, changed tag nesting, different attribute patterns — risks breaking existing rendering for data already in the system, and is exactly the "pushing sand" failure mode we must avoid.

**What is in scope for FR-1:**
- Stopping the save path from *stripping* HTML that the editor already produces (line breaks, underline, HR, font size).
- Fixing the paste handler so content lands at the cursor position.
- The generated HTML structure must be **identical** to what the editor produces today. No new tags, no changed nesting, no reformatting.

**What is explicitly out of scope for FR-1:**
- Changing the HTML tags the editor emits (e.g., switching `<br>` to `<p>`, or `<font>` to `<span style="...">`, or any equivalent "modernization").
- Changing how the PDF renderer or HTML print view interprets the narrative HTML.
- Any cleanup or normalization of stored narrative HTML beyond what is required to stop stripping.
- Any changes to `pdf-version/index.js` or the print CSS for FR-1. If a formatting issue surfaces in PDF/HTML after FR-1 is fixed, that is a separate defect outside this release.

**Compatibility requirement:** The fix must work correctly for existing case data already stored in CouchDB (which may contain the stripped form of the HTML) as well as new data entered after the fix. The fix is on the save path only — it must not reprocess or migrate old stored content.

#### FR-1.1 — Line break persistence

**Defect location:** `mmria_get_narrative_save_snapshot()` (or the caller that writes to `g_data.case_narrative.case_opening_overview` before save). The prior fix candidate involves `textarea_control_strip_html_attributes()` being called on save, which strips `<br>` and paragraph markup before the value is persisted.

**Resolution mechanism:**
1. Audit `mmria_get_narrative_save_snapshot()` and every HTML transformation applied to the narrative value on the save path.
2. Identify the specific call that is removing `<br>` tags. The candidate is `textarea_control_strip_html_attributes()` at ~line 4356 in `case/index.js` (currently commented out — this is the prior fix).
3. The fix is: **stop calling the stripping function on the narrative field** (or scope it so it does not apply to the narrative). Do not replace it with a different sanitizer that produces different HTML. The editor's native output is the authoritative format.
4. If security sanitization is still required on the save path (removing executable attributes such as `onclick`, `javascript:` hrefs), that must be done without altering structural tags or the tag/attribute patterns already present in stored data.
5. Verify with a round-trip test: enter narrative with explicit `<br>` line breaks → save → reload → confirm breaks are present in editor view and that the stored HTML is byte-for-byte the same as what the editor produced.

#### FR-1.2 — Formatting persistence (underline, HR, font size)

**Defect location:** Same save path as FR-1.1. The same stripping call likely removes `<u>`, `<hr>`, and `<font size="...">` tags produced by the editor's toolbar actions.

**Resolution mechanism:**
1. After fixing FR-1.1 (stopping the strip call), test underline (`<u>`), horizontal rule (`<hr>`), and font size (`<font size="...">` or equivalent tag the editor natively emits) for round-trip persistence.
2. If stopping the strip call does not fully resolve FR-1.2, identify the additional stripping location. Do not add new tag-emission logic — only remove stripping.
3. Do not change the tags the editor emits to represent these three formatting types. If the editor today emits `<font size="4">`, that is what must be preserved and what the PDF/HTML view must continue to receive. No tag substitution.

**PDF/HTML view:** No changes to `pdf-version/index.js` or print CSS are in scope for FR-1. The expectation is that preserving the editor's native HTML is sufficient, because print and PDF currently render correctly — the only problem is that the tags are being stripped before reaching them.

#### FR-1.3 — Cut/paste cursor integrity

**Defect location:** `page_render_create_onpaste_event()` in `case/index.js`. The paste handler does not reliably insert at the cursor position — content lands at random DOM positions.

**Root cause:** Cursor/selection state is not captured before the paste operation executes. The `window.getSelection()` / `document.execCommand('insertHTML')` sequence can lose selection state if the paste event handling re-focuses the element or if a stale selection range is used.

**Resolution mechanism:**
1. In the paste handler, capture `window.getSelection().getRangeAt(0)` synchronously at the top of the event handler — before any DOM manipulation.
2. Delete the currently selected content (if any) from the captured range.
3. Insert the cleaned paste content at the captured range using `range.deleteContents()` + `range.insertNode(...)`.
4. After insertion, collapse the range to the end of the inserted content and restore with `selection.removeAllRanges(); selection.addRange(range)`.
5. Do **not** use `document.execCommand('insertHTML')` — its selection behavior is non-deterministic across browsers; use the Range API directly.
6. The paste cleaning step must not change the HTML structure of the pasted content beyond stripping genuinely unsafe executable attributes. Strip `onclick`, `onerror`, `javascript:` hrefs, and equivalent XSS vectors. Preserve all structural tags.
7. Validate in Edge and Chrome (NFR-1) with multiple sequential paste operations targeting different cursor positions.

### FR-2 — Vitals Field Validation

#### 2.1 Config document schema

Add a new top-level key `vitals_ranges` to the existing CouchDB configuration document. Value is a JSON object mapping field names to `{min, max}` pairs. Specific range values are pending OI-1 (program team must define them before implementation).

**Schema (structure only — values are placeholders until OI-1 is resolved):**

```json
{
  "vitals_ranges": {
    "temperature":   { "min": 0.0,  "max": 0.0,  "label": "Temperature (°F)" },
    "pulse":         { "min": 0,    "max": 0,    "label": "Pulse (bpm)" },
    "respiration":   { "min": 0,    "max": 0,    "label": "Respiration (breaths/min)" },
    "bp_systolic":   { "min": 0,    "max": 0,    "label": "Systolic BP (mmHg)" },
    "bp_diastolic":  { "min": 0,    "max": 0,    "label": "Diastolic BP (mmHg)" }
  }
}
```

The `label` string is used in the Section 508 modal message (FR-2.2).

**Field name keys must match the HTML input `name` attributes as rendered by `chart.js`** — confirm exact attribute names during implementation.

#### 2.2 Server-side loading

Extend `OverridableConfiguration` (or the CouchDB config loader) to parse and hold `vitals_ranges` on startup. Options:

- **Option A (preferred — minimal change):** Deserialize `vitals_ranges` from the config document into `detail_list` as a `DBConfigurationDetail` entry with key `"vitals_ranges"`. Expose via `configuration.GetDetail("vitals_ranges")`.
- **Option B (if `DBConfigurationDetail` shape doesn't fit):** Add a dedicated `VitalsRanges` dictionary property to `OverridableConfiguration`, loaded from the `vitals_ranges` key in the raw config JSON.

Choose whichever option requires fewer schema changes to `OverridableConfiguration`. Do not introduce a new configuration class or service.

#### 2.3 Client-side delivery

**Constraint (NFR-3):** No per-event network requests. Ranges must be available synchronously at blur time.

**Mechanism: JavaScript global injected at page load via Razor.**

In the appropriate Razor view or layout partial (the one that renders the case form pages), inject:

```html
<script>
  window.mmria_vitals_ranges = @Html.Raw(Json.Serialize(Model.VitalsRanges));
</script>
```

Where `Model.VitalsRanges` is the `vitals_ranges` object read from `OverridableConfiguration` at the controller level and passed to the view. If vitals ranges are not available (null or empty — pending OI-1), the script block should set `window.mmria_vitals_ranges = null;` so the client can safely skip validation.

**Do not** add vitals ranges to the `get_case_set()` API response — this avoids changing the API contract.

**Which Razor view:** Identify the layout or view that renders the case editor forms (the page that loads `case/index.js` and the form renderer). Add the script block there. This ensures ranges are available before any form interaction.

#### 2.4 Validation logic — `chart.js`

`chart.js` in `wwwroot/scripts/editor/page_renderer/` renders vitals grids and is the single implementation point for all four forms. This avoids per-form duplication (satisfying FR-2.4).

**Add a blur handler to vitals input fields:**

```javascript
// Attach on grid render, inside p_post_html_render or equivalent post-render callback
function mmria_vitals_validate_on_blur(event) {
    var fieldName = event.target.name;  // e.g., "temperature"
    var value = parseFloat(event.target.value);

    if (!window.mmria_vitals_ranges || !window.mmria_vitals_ranges[fieldName]) {
        return; // No config loaded — skip validation (OI-1 not yet resolved)
    }

    var range = window.mmria_vitals_ranges[fieldName];

    if (!isNaN(value) && (value < range.min || value > range.max)) {
        event.target.value = '';  // Clear invalid value (FR-2.1)
        mmria_vitals_show_range_modal(range);  // Show 508-compliant modal (FR-2.2)
    }
}
```

**Attach point:** In the post-render callback for vitals grid inputs in `chart.js`. Follow the existing `p_post_html_render.push(...)` pattern used elsewhere in the codebase.

**Grid coverage:** The same handler covers all four target grids because `chart.js` renders all of them. Verify the four paths are all routed through the same rendering code in `chart.js`:
- `er_visit_and_hospital_medical_records/vital_signs`
- `prenatal/routine_monitoring`
- `other_medical_office_visits/vital_signs`
- `medical_transport/transport_vital_signs`

**Auto-save safety:** The blur validation fires at field-leave time and clears the value in the DOM input before any save trigger can read it. Since save reads from the DOM (or from a bound data model), an out-of-range value cleared by blur will not be present when a save trigger fires. This is the correct sequence and does not require changes to the auto-save mechanism.

#### 2.5 Section 508 modal (FR-2.2)

**Requirements:**
- `role="dialog"` and `aria-modal="true"` on the dialog container
- `aria-labelledby` pointing to the dialog's heading element
- Focus moves to the dialog on open (call `.focus()` on the first focusable element)
- Focus is trapped inside the dialog while open (Tab / Shift+Tab cycle only within the dialog)
- Dialog is dismissible by keyboard: Enter or Space on the close button, Escape key
- On close, focus returns to the vitals input field that triggered the modal

**Modal content:**
```
{field label} must be between {min} and {max}.
For example: Temperature must be between 88 and 110.
```
(Values from `range.label`, `range.min`, `range.max`)

**Implementation:** Inject a single modal HTML fragment once into the case page DOM. Reuse for all vitals fields (populate dynamically). Follow any existing accessible modal pattern in the codebase. If none exists, implement from scratch per the requirements above. Do not introduce a third-party modal library.

#### 3.4 JavaScript global for client-side config values

Inject a `window.mmria_system_config` global at page load, alongside `window.mmria_vitals_ranges` (FR-2.3). In the same Razor script block:

```html
<script>
  window.mmria_vitals_ranges  = @Html.Raw(Json.Serialize(Model.VitalsRanges));
  window.mmria_system_config  = @Html.Raw(Json.Serialize(Model.SystemConfig));
</script>
```

Where `Model.SystemConfig` includes at minimum `{ "omb_expiration_date": "..." }`. Both globals are set in a single script block to avoid multiple inline scripts.

**If this Razor view is not a form page** (i.e., `_Footer.cshtml` and `_BurdenStatement.cshtml` are layout-level), then a common filter or action filter can populate `ViewData["OmbExpirationDate"]` and `ViewData["MmriaVersion"]` for every request. Investigate whether a `BaseController` or existing action filter is the right extension point. Do not duplicate controller logic across multiple controllers.

#### 3.5 Developer update workflow (FR-3.3)

No admin UI. The workflow is:

1. Developer edits the CouchDB config document (either directly or via the database-scripts source file).
2. Developer runs the existing production update script.
3. Script deploys the updated config document to CouchDB.
4. Application server restarts (or a targeted config reload is triggered if the system supports hot reload of config docs).
5. All render surfaces reflect the new values.

**Architectural note:** If the application does not currently support hot-reload of the config document without restart, that is out of scope for V4.1. A restart is acceptable for developer-managed config changes.

## 4. Implementation Patterns

This is a brownfield maintenance release. The following patterns apply to all V4.1 work:

### 4.1 Server-side

- Follow the SharedLibraries pattern: thin controllers, business logic in `mmria.common/SharedLibraries/<Feature>/Manager`, CouchDB access in `<Feature>/DAL`.
- Config access: `tenantRuntime.RequireConfiguration()` → `configuration.GetString(key)`. Do not bypass this with raw CouchDB reads.
- Do not add `try/catch` wrappers to Manager or DAL methods. Let failures propagate.
- Use `CouchDbHttpClient` for any CouchDB HTTP calls. Do not introduce `new HttpClient()`.
- Async all the way: no `.Result`, `.Wait()`, `.GetAwaiter().GetResult()`.

### 4.2 Client-side

- Follow the existing vanilla JavaScript patterns in `wwwroot/scripts`. No new libraries.
- Use the `p_post_html_render.push(...)` pattern for event binding that must run after DOM insertion.
- Do not use `document.execCommand(...)` for DOM manipulation in the paste handler — use the Range API.
- Section 508: any new interactive element (modal, dialog) must be keyboard-navigable and focus-managed.

### 4.3 Config key naming

All new CouchDB config keys introduced by V4.1:

| Key | Type | Used by |
|---|---|---|
| `vitals_ranges` | JSON object | FR-2, server-side and client-side |
| `omb_expiration_date` | String | FR-3.1, server-side (Razor) and client-side (form renderer) |
| `mmria_version` | String | FR-3.2, server-side (Razor footer) |

### 4.4 JavaScript global naming

| Global | Type | Used by |
|---|---|---|
| `window.mmria_vitals_ranges` | Object `{ [fieldName]: { min, max, label } }` | FR-2 blur validation in `chart.js` |
| `window.mmria_system_config` | Object `{ omb_expiration_date: string }` | FR-3.1 label renderer in `page_renderer.js` |

Both globals are set to `null` if the config is not available, so client code must null-check before reading.

- Retroactive correction of existing out-of-range vitals data in CouchDB
- Admin UI for any configuration value
- PMSS print dropdown changes
- New services, infrastructure, or external dependencies
- Any SharedLibraries migration or controller cleanup beyond what is strictly required to wire FR-3 config values
