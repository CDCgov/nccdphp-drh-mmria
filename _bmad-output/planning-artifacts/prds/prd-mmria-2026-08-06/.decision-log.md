## 2026-08-20 — FR-2.8 and FR-2.9 added (Vital-Import Save Regression Fix)

**Decision:** Add FR-2.8 (Vital-Import Dedicated `VitalImportCaseWriter`) and FR-2.9 (`BatchItemProcessor` exception hardening) under Epic 29 to fix the batch-import regression introduced by Story 29.7.

**Root cause (confirmed by code inspection and git-history diff):** Story 29.7 rewired `BatchItemProcessingService.Process_Message` to save new cases via `CaseManager.SaveCaseAsync` in order to reuse Story 29.1's server-side record-id format/uniqueness guards and Story 29.4's collision-retry loop. Pre-29.7 the batch wrote raw via `_caseRepository.PutCaseDocumentJsonAsync` using the CouchDB service credentials — no `ClaimsPrincipal`, no application-layer authorization. Story 29.7 introduced `BuildVitalImportPrincipal` which fabricates a synthetic `ClaimsPrincipal(name="vital-import", issuer="https://contoso.com")`. That principal has no role/jurisdiction entries in the `jurisdiction` database, so `authorization_case.is_authorized_to_handle_jurisdiction_id` returns false and `SaveCaseAsync` responds `ok: false, error_description: "unauthorized PUT / : {caseId}"`. Every batch save now fails at the authorization gate.

**Design options considered:**

- **A (bypass flag on `SaveCaseAsync`):** rejected — a `bypassAuthorization: true` boolean parameter on a method shared with controllers is a latent security risk. A future controller call site could set it accidentally.
- **A3 (marker type):** considered — compile-time-safer than A, but keeps two very different operations (user request vs server integration) on one method signature, which harms readability.
- **A4 (real `vital_import` role):** considered — architecturally cleanest single-auth-path model. Rejected as overbuilt for a single server-side case-writing integration. Would require per-tenant role-assignment provisioning in the `jurisdiction` database, a reserved-username prefix convention to prevent login as `vital-import`, startup health checks, and a new role case in `authorization.cs`. The infrastructure is worth building when a second server integration needs case-write rights — not before.
- **A1 refined to `VitalImportCaseWriter` (selected):** dedicated writer class in the vital-import feature folder, purpose-named method (`SaveNewVitalImportCaseAsync`), no `ClaimsPrincipal` parameter at all, `internal` visibility, registered only in the vital-import service DI graph. Controllers cannot resolve it, and its signature has no plausible use in a user-request codepath. Story 29.1 record-id format/uniqueness guards and Story 29.4 collision-retry are preserved via a shared private helper on `CaseManager` — no behavioral drift between the two save paths.

**Guardrails against future misuse:**
- Location (`mmria.services/SharedLibraries/VitalImport/Manager/`) signals feature-local scope.
- Purpose-specific method name (`SaveNewVitalImportCaseAsync`) resists opportunistic reuse.
- No `ClaimsPrincipal` parameter — a controller reaching for this would have to actively discard its authenticated identity, an obvious code-review anomaly.
- `internal` visibility + DI registration only in vital-import service.
- Unit test asserts `SaveCaseAsync` with a synthetic-name `ClaimsPrincipal` still returns `unauthorized PUT` (prevents someone from re-adding a bypass path to the user method later).

**Second bug uncovered during investigation:** `BatchItemProcessor.ReceiveAsync` silently catches exceptions from `Process_Message` without notifying the parent `BatchProcessor`. Result: exceptioned items leave `pending_items > 0` forever, `Finalize_Batch()` never runs, and the affected items stay visible under "In Process" in the batch status UI indefinitely. FR-2.9 (Story 29.9) hardens this by `Tell`-ing a synthetic `ImportFailed` `BatchItem` back to the `BatchProcessor` on catch. Independent of FR-2.8; can be worked in parallel.

**Scope of amendment to FR-2.7:** FR-2.7's outcome — batch imports get Story 29.1 guards and Story 29.4 collision-retry — is preserved. FR-2.7's implementation mechanism ("route batch writes through `SaveCaseAsync`") is superseded by FR-2.8's dedicated writer. Story 29.7 status changes from `review` to `superseded` for audit purposes; the code work it delivered (retry loop shape, `document_put_response.error_code` handling, batch-local dedup HashSet) is preserved by Story 29.8.

**Revisit condition:** If a second server-side case-writing integration lands (e.g., replication starts creating cases), re-evaluate A4 (role-based) as the shared substrate. Adding a second writer method is fine; adding a third is a smell.
